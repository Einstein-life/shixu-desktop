# Shixu Desktop 2.0：湿实验工作流改进方案

## 湿实验人员需求总结

湿实验的一天通常以实验节点和样本状态为中心：核对样本、准备试剂与仪器、执行手工步骤、等待孵育或设备运行、按时接手，再记录结果、偏差和原始文件位置。常见问题不是“缺一个总待办”，而是信息散落在纸本、计时器、电子表格和聊天里，离开实验台后难以恢复上下文。

常见需求可归为五点：

1. **及时接手：** 同时运行多个孵育或设备步骤，用户需要看到哪个节点先到、是否逾时，并收到清楚的提醒。
2. **合理安排等待时间：** 5–30 分钟的空档可用于记录、文献或行政工作，但不能把有明确接手时间的窗口排满。
3. **样本和批次不混淆：** 快速记录样本号、批次、试剂批号、仪器/位置、执行人和关联项目；开始前核对准备清单。
4. **保留可恢复上下文：** 记录实际起止、结果、偏差、照片或原始文件路径，以便复现、写记录、交接和复盘。
5. **遵守实验室规范：** 工具提供可编辑的工作流和计算，不自行推断实验条件；本实验室批准的 SOP、试剂说明和仪器规程始终是操作依据。

这些是通用工作流假设。发布前应邀请分子生物学、细胞、生化、组织学等不同方向的实验人员访谈和试用，核实步骤、提醒和记录字段是否适配各自实验。

## 2.0 已实现

- **实验执行台：** 创建/编辑实验，关联项目、样本/批次、试剂批号和仪器；记录准备清单与有序步骤。
- **步骤计时：** 区分人工操作和等待步骤，显示预计结束、逾时和容许延迟。用户确认完成后才能启动下一步。
- **等待时建议：** 依据下一接手时间和任务时长留 2 分钟返回缓冲；人工操作或到时步骤优先显示。
- **本地实验记录：** 记录开始、确认完成、取消计时、结果和偏差；重启后继续计算，到时发系统通知，支持 Markdown 导出。
- **配液计算：** 按用户输入计算稀释公式 C₁V₁=C₂V₂ 和 Master mix 总量，校验无效数据，不给出实验浓度建议。
- **英文界面：** 主窗口、悬浮窗和系统托盘共用语言设置；实验人员填写的样本名与记录保留原文。
- **数据可靠性：** 迁移 v1 数据并保留备份；自动保存采用临时文件替换；不同窗口同时修改时合并独立字段。

## 分阶段改进

### 2.0.x：打磨单人日常工作流

验证应用启动、休眠恢复和多计时器队列；完善窄屏/键盘操作、搜索、备份导入导出、提醒延迟与静音时段。提供由实验室自行维护的空白结构模板，时间仅作排程估算，不内置未经验证的实验参数。

### 2.1：样本批次与标准化记录

增加实验批次、样本表导入、管/孔板位置、重复次数、实验员、方案版本、偏差、质控结论和结果文件链接。复制实验计划时重置执行时间和结果，保留历史记录不被覆盖。先与选定实验室共同验证一个方向，例如 PCR/qPCR，再扩展。

### 2.2：试剂和仪器准备

按需支持库存/柜位、开封日期、批号、有效期、低库存提醒、仪器时间预约与维护提醒。优先识别“开始前缺料或设备不可用”，再评估二维码/条码。支持 CSV 往返，避免强迫实验室替换已有库存系统。

### 2.3：多人交接与共享

只有在用户确认需求后再设计责任人、交接、权限、审计和样本流转。共享功能需明确主机、加密、访问权限、备份和离线策略；默认继续本机存储。不自动上传个人数据，也不宣称具备合规电子实验记录认证。

## 关键交互规则

- 计时结束表示“到计划接手时间”，不是实验成功；须由操作人员确认实际完成。
- 准备清单未完成时不启动实验；运行中的步骤不可通过编辑覆盖。
- 应用关闭或设备休眠可能延迟系统提醒；恢复后显示逾时并说明时间，不承诺必然准时送达。
- 提醒按步骤清楚呈现，允许用户延后/静音；实验节点先于普通待办。
- 并行建议只显示能在接手前完成的任务，并留出返回缓冲；没有合适事项时直接说明。
- 模板时间是用户输入的排程估算，不是通用实验方案；所有配液结果须自行核对单位与 SOP。
- 为将来可追溯记录预留实验员、样本/批次、方案版本、试剂批号、仪器、原始文件、偏差和结果等字段；未采集的信息不能被暗示已记录。

## 使用率验证

邀请 8–12 位不同方向的实验人员，观察准备、启动计时、切换步骤、处理样本和写记录的过程。访谈可问：最近因计时节点错过/延迟是什么情况？同时用了哪些计时器或纸本？哪类信息必须留在正式记录？何种任务适合 5、15、30 分钟空档？谁维护 SOP 模板、如何确认版本？

以试用前两周为基线，追踪实验台页使用人数、每周回访、完整实验记录率、到点确认率、手动覆盖/取消次数、用户新增实验和持续使用的实验室比例。重点判断提醒是否降低遗忘、记录是否减少交接时间、两周后用户是否愿意继续使用；安装量单独不能代表价值。


## 现有代码评估与产品定位

本次检查的 Windows/macOS 主进程、主页面和悬浮窗文件哈希一致，版本均为 1.1.3。旧版已有任务优先级、人工/分析等待、项目里程碑、工时累加、回看和 JSON 迁移能力。原版 Python + HTML 的本机桥接与 Electron 是不同入口，2.0 优先复用 Electron 能力，统一一套跨平台源码，避免在三个版本重复开发。

现有产品对湿实验的主要缺口如下：

| 现状 | 对实验人员的影响 | 2.0 取舍 |
| --- | --- | --- |
| 待办主要按日期档位和分数排序 | 20 分钟后必须接手的实验会被普通高分任务掩盖 | 实验步骤独立计时，到时优先呈现；任务分数只辅助安排 |
| 等待是单个任务的状态 | 不知道等待何时结束，也无法表示手工/等待交替 | 在实验中增加有序步骤、预计时长与实际开始/完成时间 |
| 任务以标题和结果备注为核心 | 样本、批次、位置和试剂信息容易混在标题里 | 增加实验字段和准备清单；复杂样本管理分期做 |
| 周工时近似累计活跃任务历史工时 | 跨周的长任务容易让“本周投入”偏高 | 先明确它是估算；后续升级为带日期的工时事件 |
| 主窗口与悬浮窗传整个数据快照 | 并行修改可能覆盖新增实验字段 | 共享迁移层与字段差异合并；同字段同时修改仍需后续冲突提示 |
| 大量中文写在内联页面里 | 国际实验室难以使用，也不利于持续维护 | 独立翻译资源、生成英文入口、语言状态持久化、用户内容不翻译 |

建议定位为“科研人员的实验执行与时间协同助手”。它应在打开当天就提供可见收益：下一步是什么、什么时候接手、现在能做什么、做过什么。先保留现有生信/写作工作流，让同一个人可以在实验等待时推进分析、论文和会议准备；完整库存系统、复杂 ELN 和多人 LIMS 不应成为 2.0 的前置门槛。

## 优先级与具体验收

P0 表示首批试用必须可靠，P1 表示需求验证后优先增强，P2 表示依赖团队与治理设计。下面的“验收”是目标标准；源码已实现的范围以本文前面的清单为准，并不代表都已完成桌面验收。

| 优先级 | 需求/功能 | 具体设计 | 验收标准 |
| --- | --- | --- | --- |
| P0 | 多实验节点管理 | 每个实验独立步骤、时长、状态、接手窗口；同一实验按顺序推进 | 三个实验并行时最早节点可见；步骤完成后下一步不自动启动 |
| P0 | 断点恢复 | 保存绝对 dueAt 与 actual timestamps；重启按时间重算 | 关闭 10 分钟后重新打开，不能重新从完整时长开始计时；已到时应显示 |
| P0 | 准备核对 | 用户自建清单，样本/对照/试剂/仪器准备完成才能开始 | 未完成清单时禁用启动并给出明确原因；试剂仍由操作者核验 |
| P0 | 可解释的并行建议 | 根据最近接手点减缓冲时间，以单项任务预计时长筛选 | 等待 20 分钟时不推荐 30 分钟任务；人工操作和已到时情况停止建议 |
| P0 | 本地数据保护 | 导入前确认、备份、格式校验、故障恢复、v1 到 v2 迁移 | 导出后可在另一份配置恢复实验与任务；坏文件不能无提示覆盖好数据 |
| P0 | 英文界面 | 四个主视图、表单、空状态、错误提示、悬浮窗、原生菜单 | 切换后重启仍记得语言；中文样本名和自定义 SOP 原文不变化 |
| P1 | 时间窗口语义 | 区分最早可接手、目标接手、最晚允许接手；配置提前提醒 | 能表示过夜步骤、固定取样时点和可延后节点；超窗由用户记录偏差 |
| P1 | 模板版本 | 独立模板库，版本/作者/SOP链接；运行实例冻结模板副本 | 修改模板只影响未来实验，不能改写过去执行记录 |
| P1 | 结果与偏差 | 结果分类、原始文件位置、偏差原因、质控结论和复做关联 | 失败/无效实验能被记录与检索，不会因“未完成”消失 |
| P1 | 周报整合 | 展示完成实验、失败/复做、关键产出、阻塞、下周采样/仪器节点 | 报告可以直接解释项目推进；明确区分等待时长与人工工时 |
| P1 | 批量样本与孔板 | CSV导入、唯一ID、位置映射、分组/重复、缺失数据检查 | 导入前预览；重复编号、空位置和超板位明确报错；导出保持对应关系 |
| P2 | 共享仪器 | 预约冲突、维护不可用、前后清洁缓冲、负责人 | 不允许同台设备同一时段重复占用；支持取消与变更记录 |
| P2 | 库存/冻存位置 | 批次、到货/开封/到期、余量单位、箱盒位置 | 相同试剂不同批号不合并；低库存只是提醒，不自动扣错账 |
| P2 | 团队交接 | 指派/接受/完成、交接备注、权限与离线冲突处理 | 接手人员清楚看到样本、当前步骤、下一节点和未解决风险 |

## 三类试用场景

**分子实验人员：** 上午同时进行一批 PCR 和另一批样本处理。新建批次、核对样本和对照，启动设备等待；空档推荐 15 分钟整理样本表；到时提醒接手并记录结果文件路径。价值验证是减少切换应用和遗忘，不是缩短仪器运行时间。

**细胞或长周期实验人员：** 工作跨多个自然日，有固定取样点、培养观察和周末安排。2.0 现有单次步骤可以辅助记录，但绝对取样时间、周期复发和跨日依赖尚需 P1 实现。不要用通用倒计时冒充细胞状态判断；排程输入应来自既定方案和人工观察。

**平台/共享仪器人员：** 需要协调用户、设备、样本到达与质控。先验证单次实验记录能否减少交接遗漏，再加预约与权限；多人同时修改和样本链路不应简单建立在个人 JSON 文件共享上。

## 数据结构与工程实施建议

保持实验对象与待办对象分离，通过 project_id 关联，避免给每个普通待办堆大量实验字段。实验实例包含 sample/batch、equipment、lot、checklist、steps、events 和 notes；步骤记录 kind、planned minutes、tolerance、status、startedAt、dueAt、completedAt。后续把 SOP 版本、实验员、QC状态和结构化结果作为显式字段扩展。

数据版本已升级为 4；迁移应补齐缺失 ID、保留未知业务字段，且保证同一份数据多次载入不会反复生成新 ID。导入文件验证通过后再覆盖当前库，保留可恢复备份。正式版应补足事件级更新、同字段冲突提示、操作撤销和可配置备份轮换。

共享一套 Electron 主进程和 renderer 代码，在 Windows 与 macOS 分别构建。以系统差异处理通知、托盘、登录启动、多显示器和窗口置顶；不要把平台修复手工复制到两套目录。源码中的实验时钟采用绝对时间，而不是每秒递减保存数值；它能在恢复时显示逾时，但系统睡眠或应用退出期间不能保证通知到达。

英文工程需要统一术语：Project、Task、Experiment、Step、Hands-on、Wait、Due、Overdue、Reagent lot、Deviation、Result note。日期用本地语言格式，数据保存标准时间；µL/mL、浓度和时间单位显式呈现。测试需覆盖长英文按钮、中文用户字段、引号/尖括号、空项目、旧数据、两窗口修改和无通知权限。

## 推广与采用策略

1. 首次启动让用户在“科研任务”和“实验执行”两条入口中选择，提供可跳过的 60 秒引导；优先邀请创建一个真实实验，而不是先要求整理全部项目。
2. 对每个合作实验室只共建 1–2 个高频模板。由实验室确认字段和 SOP 版本，记录维护者；模板可导入导出，让新成员能直接使用熟悉流程。
3. 用一次完整实验的样本准备、等待利用、到时接手、结果归档展示价值；示例使用合成数据，避免把真实研究信息作为产品演示。
4. 提供一页中英对照操作卡和短演示；说明离线、数据位置、备份与提醒的实际边界，降低“研究数据会上传”的顾虑。
5. 收集反馈时问具体步骤而非笼统满意度：哪次提醒没有看到、哪个字段重复填写、哪个按钮不敢点、什么记录被迫回到 Excel。
6. 采用指标以用户主动同意的访谈/本地导出为起点。当前版本不内置统计上传；如将来增加遥测，需单独设计同意、字段最小化和关闭方式。

## 建议试点排期与发布门槛

这是相对排期估算，按单名开发者与实验室可用时间调整，不是交付承诺。

- 第 1 周：8–12 人访谈，选定最窄试点场景，记录现有错误/耗时基线。
- 第 2–3 周：用 2.0 beta 完成真实流程试用，修复记录保存、步骤切换、语言与提醒问题；不在这阶段扩建多人平台。
- 第 4 周：两周回访，比较完整记录率、继续使用率和提醒是否有帮助；决定进入 2.1 或继续打磨。
- 正式版前：Windows 10/11 与 macOS Intel/Apple Silicon 分别安装、升级、导入/导出、睡眠恢复、多屏、通知权限和卸载保留数据测试；必须保存测试结果。

本次交付是 2.0.0-beta.1 源码与方案。已完成的自动检查不等于安装包/系统通知/睡眠恢复验收；实际桌面可视化和 macOS 构建尚需完成，不能据此对外宣称正式版已经发布。
